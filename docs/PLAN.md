# WTE（What To Eat）「今天吃什么」—— 方案计划书

> 版本：v1.2（已实施）  
> 目标平台：Windows 桌面（可移植到 macOS / Linux）  
> 语言/工具链：Rust 1.97.1，单 crate，纯离线  
> **实施状态（2026-11-13）**：egui / eframe 0.32.3 版本已完成；release 3.0 MB，题库 118 道（清理 10 道不适合外卖的菜品），单测全绿。  
> v1.2 变更：取消预算题和预估价格，改为 5 题（餐段/口味/汤水/主食/辣度）；价格交给下单平台。  
> v1.1 变更：第一题改为「早饭/午饭/晚饭/都行」；点选项自动进入下一题，保留上一步/下一步。细节见 `docs/NOTES.md`，使用说明见 `README.md`。

## 1. 项目概述

一个帮助用户决定「今天吃什么」的小工具：

1. 通过多轮选择题（甜/咸、带汤/不带汤、饭/面、辣度、预算……）逐步缩小范围；
2. 最终结果**一定是外卖主食**（饭、面、粉、汉堡、炸鸡、饺子、麻辣烫等），不会推「一杯奶茶」；
3. 面向「不做饭、只点外卖」的场景，内置常见外卖菜品库；
4. **完全离线、不接 AI、不联网**，数据与逻辑都在本地。

### 硬性约束

| 约束 | 落实方式 |
|---|---|
| 多次提问 | 5 道单选题，每道可「都行/跳过」，支持上一步 |
| 结果必须是主食 | 菜品模型里 `base` 字段只有「饭 / 面 / 其他主食」三值，没有主食标签的条目进不了库 |
| 点外卖场景 | 内置外卖常见菜品 + 可加载用户自己的 `menu.txt`（店里的菜单） |
| 离线、不用 AI | 纯规则筛选 + 加权随机，无网络依赖（不引入 reqwest/hyper/tokio） |
| 轻量 | 单可执行文件，无 WebView、无运行时安装、无后台服务 |

## 2. 功能范围

### MVP（本次实现）

- 欢迎页：菜品库统计、开始按钮；
- 5 道选择题：口味、汤水、主食形态、辣度、预算；
- 结果页：菜名 + 标签 + 参考价 + 推荐备注 + 3 个备选；
- 「换一个」重新抽，不重复刚才出现过的结果；
- 「重新选」回到第一题；
- 自定义菜单：读取可执行文件旁的 `menu.txt`，支持重新加载与错误行提示；
- 设置页（轻量）：显示菜品库来源、数量、文件路径。

### 暂不做（后续可选）

- 按真实位置抓取外卖平台菜单（需要联网 + 平台账号/接口，违背约束 4）；
- 历史记录 / 收藏 / 云同步；
- 多人投票、图片、营养分析；
- 手机端。

## 3. 技术选型

### 3.1 候选对比

| 方案 | 类型 | 成熟度 | 许可 | 体积 / 依赖 | 中文字体 | 本机可直接构建 | 评价 |
|---|---|---|---|---|---|---|---|
| **egui / eframe 0.37** | 即时模式 GUI，OpenGL(glow) | 很成熟（crats.io 累计 2470 万下载） | MIT / Apache-2.0 | 单 exe 约 5–8 MB；依赖树中等 | 需运行时加载系统字体（已确认 `msyh.ttc` 存在） | ✅ GNU 工具链可用 | 开发最快、最稳，**推荐** |
| **ZSUI 0.3.0-alpha.2** | 原生 Win32/AppKit/Linux 自绘 | 预发布（2026-07 首发，下载量 122） | MPL-2.0 | 原生、可裁剪，体积估计 3–8 MB | 使用系统字体，中文开箱即用 | ❌ 需 MSVC + VS C++ 生成工具（本机未装），且 msvc std 未安装 | 理念契合，但 alpha + 工具链门槛 |
| iced 0.13+ | Elm 架构 GUI，wgpu | 成熟 | MIT | 依赖较重，首次编译慢 | 需字体配置 | ✅ | 结构清晰，但对这个小程序偏重 |
| Slint | 声明式 UI | 成熟 | GPLv3 / 商业授权 | 运行时较小 | 好 | ⚠️ 许可需确认 | 许可是主要顾虑 |
| Tauri | WebView + 前端 | 成熟 | MIT/Apache | 依赖系统 WebView2，体积大 | 好 | ✅ | 对「小工具」太重 |
| ratatui（TUI） | 终端界面 | 成熟 | MIT | < 1 MB | 终端字体 | ✅ | 最轻，但不是图形窗口 |
| 纯 Win32 FFI（手写） | 直接调 user32/gdi32 | — | 无依赖 | 约 0.3–0.5 MB | 系统字体 | ✅ 仅需 mingw 库 | 最轻、无依赖，但 unsafe 代码多、开发慢 |

**关于 WebView（常见误解）**：egui / eframe **不使用、也不依赖 WebView**。它的原生后端是 `winit`（窗口与输入）+ `glow` / `wgpu`（OpenGL / Vulkan 绘制），界面由 Rust 直接画，不含 HTML/CSS/JS，也不需要 WebView2 运行时，断网、无浏览器同样可跑。ZSUI 同样是无 WebView 的原生实现（Win32 窗口 + 框架自绘控件）。真正依赖 WebView 的是 Tauri、Electron，以及 Dioxus 的 desktop-web 模式。

两者的差别只在**绘制方式**：

- egui：GPU 即时模式，帧循环重绘，跨平台表现一致，生态最大；
- ZSUI：贴近 Win32/AppKit 原生观感，控件在原生窗口内由框架绘制，更像系统应用。

### 3.2 本机环境实测

- `rustc 1.97.1`，默认工具链 `stable-x86_64-pc-windows-gnu`（可正常链接，已实测）；
- MSVC 工具链已安装但**未安装 msvc target 的 std**，且 VS 2019 下**没有 VC++ 生成工具（无 link.exe）**；
- Windows SDK 10.0.19041 存在；
- **cargo 联网受限**：`cargo search` 能返回缓存结果，但实际下载 crates.io 索引时报 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`；当前沙箱内无法拉取任何新依赖，需要一次性提权联网（或由你在外部终端执行 `cargo fetch`）；
- ZSUI 的 Windows 依赖是纯 Rust（`windows-sys`、`windows`、`cosmic-text`、`swash` 等，Windows 上**不带 winit**、无 C 构建脚本），理论上 GNU 工具链可以编译，但官方只承诺 MSVC，需实测确认；
- 全局 `~/.cargo/config.toml` 将 target-dir 指到 `C:/Users/Public/rmcl-target`（ASCII 路径，规避中文用户名问题），该目录在 DSH 沙箱下**不可写**，构建时需改用工作区 `target/` 或临时授权；
- 系统字体 `msyh.ttc / msyhbd.ttc / simhei.ttf` 存在，中文渲染可行。

### 3.3 最终决定（2026-11-13 已实施）

**采用 egui / eframe 0.32.3（glow 后端）。**

- ZSUI 与 egui 都不含 WebView，轻量程度接近；ZSUI 的差别是原生控件观感，但仍为 alpha（0.3.0-alpha.2），且官方构建链要求 MSVC + VS C++ 生成工具，本机未安装；
- egui 稳定、资料全、GNU 工具链直接可用；实测 release 单文件 **3.0 MB**，启动 < 1 秒，无网络依赖；
- 版本选 0.32.3 而非 0.37：0.37 把 `App` trait 从 `update(ctx, frame)` 改成 `ui(ui, frame)`，API 变动较大；0.32.3 功能完全够用、代码更稳。

核心逻辑与界面解耦，若以后仍想换 ZSUI，只需重写 `src/app.rs`，题库与算法不变。

遗留事项：ZSUI 的 GNU 兼容性没有实测（其 crate 未下载），本计划不再以它为主线。

## 4. 架构设计

```
┌──────────────────────────────┐
│            UI 层             │  egui/eframe（或 ZSUI）
│  Welcome / Quiz / Result     │  只负责画界面、发 Message
└──────────────┬───────────────┘
               │ 调用纯函数 / 状态机
┌──────────────▼───────────────┐
│           核心层             │  无 UI、无 IO 依赖，可单测
│  quiz（问题、筛选、放宽）      │
│  menu（模型、解析、合并）      │
│  rng（xorshift 轻量随机）      │

               │ include_str! / fs::read
┌──────────────▼───────────────┐
│           数据层             │
│  内置 menu.txt（约 120–160 道）│
│  用户 menu.txt（可选，覆盖/追加）│
└──────────────────────────────┘
```

### 关键设计

- `lib.rs` 承担核心逻辑，`main.rs` 只做窗口与字体；`cargo test` 不启动 GUI。
- 界面层是「状态 → 视图 → 消息 → 更新」的单向流，5 个问题共用一套渲染代码。
- 所有 Tag 用强类型枚举，解析失败带行号，避免脏数据进入筛选。

## 6. 题库与数据格式

### 6.1 菜品模型

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | String | 菜名，如「黄焖鸡米饭」 |
| `taste` | 甜 / 咸 / 皆 | 口味 |
| `soup` | 汤 / 干 / 皆 | 带汤、干拌/干锅类、都算 |
| `base` | 饭 / 面 / 其他 | **必填**，保证是主食（其他=汉堡、饺子、饼、包、麻辣烫等） |
| `spicy` | 0 / 1 / 2 | 不辣 / 微辣 / 重辣 |
| `price` | u32 | 参考人均价（元），0 表示未知 |
| `meat` | 荤 / 素 / 皆 | 可选字段，默认「皆」 |
| `note` | String | 一句话推荐/提醒 |

### 6.2 内置题库

- 覆盖：盖饭、卤肉饭、煲仔饭、炒饭、咖喱饭、烧腊饭、拌饭、寿司饭；牛肉面、小面、炸酱面、热干面、油泼面、螺蛳粉、米线、酸辣粉、拉面、炒面、炒河粉；汉堡、炸鸡、披萨、肉夹馍、煎饼、包子、饺子、生煎、卷饼、三明治、麻辣烫、冒菜、关东煮等；
- 规模：**约 120–160 道**，每道都经过「是主食 + 外卖常见」校验；
- 甜口主食会单独覆盖（蜜汁叉烧饭、照烧鸡饭、糖醋里脊盖饭、寿司、甜口拌饭等），避免选「甜口」后无结果。

### 6.3 自定义菜单 `menu.txt`

放在 exe 同目录，UTF-8 编码；一行一道菜，`|` 分隔，`#` 注释：

```text
# 名称 | 口味(甜/咸/皆) | 汤水(汤/干/皆) | 主食(饭/面/其他) | 辣度(0-2) | 参考价 | 备注
黄焖鸡米饭 | 咸 | 干 | 饭 | 1 | 25 | 微辣下饭
兰州牛肉面 | 咸 | 汤 | 面 | 1 | 22 | 清汤
蜜汁叉烧饭 | 甜 | 干 | 饭 | 0 | 28 | 偏甜
```

- 缺列/未知枚举：该行跳过，界面显示「第 12 行：口味必须是 甜/咸/皆」；
- 文件存在时**与内置库合并**（按菜名），同名条目由自定义覆盖；用户可只写自己常点的十几种；
- 界面提供「生成菜单模板」「重新加载」「打开所在文件夹」按钮，方便随手维护。

### 6.4 关于「结合位置」

外卖平台没有可离线使用的「按位置列菜单」公开接口；联网抓取又违背「离线、不接 AI」的要求。因此采用折中方案：

- 内置全国通用的外卖主食库；
- 用户把自己附近能点到的菜单/店铺菜品粘进 `menu.txt`，程序只在这个池子里筛选 —— 本质上就是「用位置信息维护答案库」，且完全离线；
- 若以后想接高德/美团，可作为可选模块（默认关闭、单独 feature），不放进 MVP。

## 7. 推荐算法

### 7.1 筛选

对每道菜，逐项比较用户已作答的维度：

```
match = true
for dim in [口味, 汤水, 主食, 辣度, 预算]:
    if 用户选了「都行」: continue
    if !compatible(dish, dim, answer): match = false
```

兼容规则：

- 口味/汤水/base：菜品的「皆」兼容任意选择；否则必须相等；
- 辣度：用户选「不辣」→ `dish.spicy == 0`；「微辣」→ `<= 1`；「重辣」→ `>= 1`；
- 预算：≤20 / 20–35 / ≥35，未知价格（0）不因预算被淘汰，只在展示时标注「价格未知」。

### 7.2 无结果时的放宽

按「用户最不敏感」的顺序逐级放宽，保证一定有结果：

```
预算 → 辣度 → 汤水 → 口味      （主食维度永不放宽）
```

每放宽一项，结果页显示「已放宽：预算」。若放宽到只剩主食维度仍无结果，则在该主食类别里随机并提示「条件太苛刻，给你挑了一道最接近的」。

### 7.3 抽取

- 候选集内均匀随机（实现上没用权重：候选已经过筛选，再加权反而不好解释）；
- 使用自实现 `xorshift64*`，种子取 `SystemTime` 纳秒（无需 `rand` 依赖，可离线、可复现测试）；
- 记录最近 10 次结果，抽取时先排除；候选被排空时才允许重复；
- 结果页最多展示 3 个备选（同样从候选集抽，不与主结果重复）。

## 8. 依赖与构建

### 8.1 依赖（主方案）

```toml
[dependencies]
eframe = { version = "0.32.3", default-features = false, features = ["glow", "default_fonts"] }

[profile.release]
opt-level = "z"
lto = true
codegen-units = 1
panic = "abort"
strip = true
```

- 不引入 `serde`（自写 `|` 分隔解析）、`rand`（自写 PRNG）、`chrono`、任何 HTTP/异步库；
- 中文字体：启动时依次尝试 `C:\Windows\Fonts\msyh.ttc` → `msyh.ttf` → `simhei.ttf`，读入注册为 fallback；找不到时界面显示英文兜底提示（不崩溃）。

### 8.2 构建命令

```powershell
$env:CARGO_TARGET_DIR = "C:\Users\Public\rmcl-target\wte"
cargo build --release --offline
# 产物：C:\Users\Public\rmcl-target\wte\release\wte.exe，再复制到 dist\
```

- 用户名含中文时，mingw `dlltool` 无法在中文 target 路径下生成 `.lib`，所以 target-dir 必须是 ASCII；
- 该路径在 DSH 沙箱外，构建时需要一次提权；普通终端里直接用全局 cargo 配置即可；
- 首次拉依赖需要联网（沙箱内 cargo 的 HTTPS 被 schannel 拒绝，需提权执行 `cargo fetch`）。

### 8.3 体积与启动（实测）

| 指标 | 实测 / 目标 |
|---|---|
| exe 体积 | **3.0 MB**（目标 ≤ 10 MB） |
| 冷启动 | 约 0.3–0.5 s（本机） |
| 运行时依赖 | 无（不装 WebView / VC 运行时） |
| 网络调用 | 0 次（依赖树里没有 HTTP 客户端；断网可运行） |

## 9. 测试计划

### 自动测试（`cargo test`）

| 用例 | 断言 |
|---|---|
| 解析正常行 | 字段、默认值正确 |
| 解析坏行 | 返回错误 + 行号，跳过该行 |
| 合并去重 | 同名菜只保留一条 |
| 主食约束 | 每道菜 `base` ∈ {饭, 面, 其他}；不存在「奶茶/蛋糕」类 |
| 口味+汤水+主食组合 | 甜/汤/面 等边界组合结果符合预期 |
| 放宽顺序 | 无结果时按 预算→辣度→汤水→口味 放宽，且主食不放宽 |
| 辣度边界 | 微辣包含 0/1，重辣包含 1/2 |
| 随机不重复 | 连续 10 次不出现重复；PRNG 固定种子可复现 |
| 预算未知 | price=0 不被预算过滤 |

### 手工验证（GUI）

- 中文显示正常、窗口缩放正常、DPI 正常；
- 5 题流程可前进/后退，答案保留；
- 「换一个」不重复、「重新选」清空；
- `menu.txt` 有错行时提示准确，修正后重新加载生效；
- 断网启动、全程无网络请求；
- release exe 双击可运行。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| ZSUI 为 alpha，API 可能变 | 返工 | 固定 `=0.3.0-alpha.2`；UI 独立模块；核心逻辑与 UI 解耦 |
| ZSUI 需要 MSVC/VS C++ 工具 | 本机构建失败 | 先做 M0 验证；不通过则用 egui，或你确认后安装 Build Tools |
| egui 默认字体无中文 | 界面乱码 | 运行时加载 `msyh.ttc`，缺失时回退 `simhei.ttf` 并提示 |
| 工作区中文路径 + GNU 工具链 | 链接/打包报错 | 已确认 rust-lld 方案；target-dir 用 ASCII 临时目录兜底 |
| 题库口味标注主观 | 推荐不准 | 标签全部写在 `menu.txt`，用户可自行改；单测覆盖边界 |
| 用户想要「按位置自动生成」 | 需求缺口 | 用 `menu.txt` 粘贴本地菜单替代；联网方案单列为后续可选 |
| 结果总是同几道菜 | 体验差 | 最近 10 次去重 + 加权随机 + 备选展示 |

## 12. 需要你确认的事项

1. **UI 方案**：按建议用 egui（今天就能跑起来），还是坚持 ZSUI（需要先装 VS C++ 生成工具并接受 alpha 风险）？
2. **自定义菜单**：`menu.txt` 这个方案是否够用？还是希望有「从剪贴板粘贴一批菜名」的导入界面？
3. **题目数量**：5 题（口味/汤水/主食/辣度/预算）够吗？要不要加「荤素」「想吃热的还是凉的」？
